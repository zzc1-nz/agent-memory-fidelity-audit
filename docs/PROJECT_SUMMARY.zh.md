# 项目总结 · Agent 记忆压缩忠实度审计基准

## 一句话

一个回答「压缩掉的到底是冗余，还是任务所需的关键事实」的基准：把两类信息故意混进 30 段长交互历史，用两种压缩范式压到同样比例，再用 300 道探测题测出**每正确答案的 token 成本**，证明「压缩率不是目标」。

## 要解决的问题

业界关于记忆压缩的指标是三类：压缩率、压缩倍数、语义连贯性。

- OpenMemX：LLMLingua-2 抽取式压缩，声称 prompt 减少 20–40% 且不丢语义连贯性
- AgentMem：405× 上下文压缩，约 873 token/会话

它们都没回答：**被删掉的 token，是冗余，还是完成任务所必需的事实？**

一段摘要可以写得非常连贯，同时恰好丢掉下一步任务需要的那个路径、端口或日期。连贯性是摘要自身的属性，忠实度是摘要相对任务的属性。前者容易测，后者才是决定能不能用的那个。

## 方法

### 数据：把两类信息都控制住

每段 20–30 轮 agent–用户对话，覆盖编码（包管理器、文件路径、API key 位置）、研究（论文引用、数据来源、截止日期）、日常（用户偏好、约束）三类任务。

刻意埋入两类内容：

- **冗余**（实测平均占 45.9% 原始 token）：重复的状态汇报、复述的构建步骤、寒暄。这是压缩**应该**删掉的。
- **关键事实**（每段 6–9 个，共 220 个，只出现 1–3 次）：这是压缩**不该**删的，并按四个维度标注：

  | 维度 | 取值 | 假设 |
  |---|---|---|
  | 出现频次 | 1 / 2 / 3+ | 低频先丢 |
  | 显著性 | 前台 / 背景 | 背景先丢 |
  | 嵌入深度 | 独立成条 / 段落中间 / 深埋长答复 | 深埋先丢 |
  | 稳定性 | 稳定 / 被覆盖 | 被覆盖的会保留旧值 |

`被覆盖` 是借 OpenMemX 分层抽象的「遗忘」机制：后一轮改写前一轮的值。保留旧值的压缩器会给出**自信的错误答案**，这是最糟的失败模式，也是这个基准专门要抓的。

### 两个压缩臂

| 臂 | 机制 | 对标 |
|---|---|---|
| 分层摘要 | map-reduce：切块 → 逐块摘要 → 归并，并在提示中强制保留标识符 | OpenMemX 分层抽象 / AgentMem 认知栈压缩 |
| 抽样式 | 确定性句子打分（TF-IDF + 标识符加权 + 冗余惩罚 + 时效性），按预算取子集并保持原序 | LLMLingua-2 式抽取压缩，零依赖自实现 |

两臂都**按预算压到约 25%**，保证比较是在同等压缩率下进行，而不是各自压到哪算哪。

### 三类探测题

| 类型 | 每段数量 | 考什么 | 预期 |
|---|---|---|---|
| 高层概括 | 3 | 主旨（目标是什么、选了哪套栈） | 摘要应能答对 |
| 具体事实 | 5 | 一个精确字面量（路径、端口、日期、引用） | 压缩可能丢失 |
| 多跳 | 2 | 组合 ≥2 个被压缩的信息点 | 最难 |

每题跑两种上下文（全量 / 压缩），由**与被测模型不同的独立模型**判定（防自我偏袒）。判定器在人工标注对上校准：14/14 一致，危险方向（接受「合理但错误」的答案）0/8。

### 核心指标

```
每正确答案 token 成本 = (上下文 token + 压缩本身花费 token) / 答对题数
```

对应的盈亏平衡推导：

```
压缩划算  <=>  准确率留存 > 压缩率
```

砍掉 75% 的 token 但只留住 60% 的答案，每个正确答案的成本反而涨了约 1.4 倍。

## 结果（30 段 / 300 题 / 166 万 token，真实模型）

| 方案 | 压缩率 | 准确率 | 答对 | 每正确答案 token | vs 基线 |
|---|---|---|---|---|---|
| 不压缩（基线） | 100% | 67.3% | 202/300 | **2,061** | — |
| 分层摘要（LLM） | 22.7% | 63.0% | 189/300 | **1,877** | -8.9% |
| 抽取式（确定性） | 24.7% | 51.0% | 153/300 | **672** | **-67.4%** |

### 三个反直觉的发现

**1. 两种范式的压缩率几乎相同（相差 2.0%），成本相差 3.1 倍。**

所以「谁压得更小」在这个规模上几乎没有区分力。真正决定工程决策的是「谁每个正确答案更便宜」，而这一项把它们拉开了几十个百分点。

**2. 抽象是资本开支，选择是运营开支。**

摘要臂在原始上下文上省了约 10,722 token/会话，但生成全部 30 份摘要本身花掉 260,121 token。它只有在每份记忆被复用约 **24 次以上** 时才开始划算 —— 这是**工作负载**的属性，不是压缩器的属性。一次性探测场景下，它严格劣于不压缩。

**3. 部分「丢失」根本不是丢失。**

84 个从对变错的题里，**53 个所依赖的事实仍逐字保留在压缩记忆中**。两种机制：

> **值混淆**：会话修订过某个值时，压缩记忆往往新旧值都留着。字面串活下来了，任何字面留存指标都给它满分 —— 但读者无从判断哪个是当前值，于是报错了那个。**检索失败**：值在记忆里，但作答模型没有把它捞出来。

这是本基准与 token 级留存指标最根本的分歧：**一个记忆可以在所有字面留存指标上拿满分，同时仍在误导人。只有答案级指标会给这件事定价。**

### 失败规律（可解释的部分）

按臂拆分的字面留存率（分母是「被探测到的事实」）：

| 维度 | 取值 | 抽样式 | 摘要式 |
|---|---|---|---|
| 嵌入深度 | 深埋 | 78.2% | 96.2% |
| 嵌入深度 | 段落中间 | 88.1% | 92.9% |
| 显著性 | 背景 | 78.5% | 92.6% |
| 显著性 | 前台 | 91.5% | 97.9% |
| 稳定性 | 被覆盖 | 83.3% | 90.0% |

抽样式在「深埋 / 背景」上的丢失率约为摘要式的 4 倍，但每个正确答案仍便宜 64% —— 因为它不花钱做判断。

按题型的丢失率：高层概括 22.8% > 多跳 11.7% > 具体事实 9.7%。**本该最容易被摘要处理的题型，反而丢得最多**，因为一个概括答案要一次性复现多个字面量。

## 工程实现

- **132 项离线单元测试**，数据集与探测题是 `(n, seed)` 的纯函数，可逐字节复现。
- **判定器独立性**由配置强制（三个不同模型），并有手工标注校准脚本。
- **全流程可断点续跑**：每完成一格就落盘，网关抖动只损失时间不损失正确性。
- **Token 计量单点收口**：所有调用经过同一个客户端，`cl100k_base` 统一计数，成本可归因到（角色、会话、策略、题）四元组。
- **修复了一个会静默毁掉结论的 bug**：`fact_id` 只在会话内唯一，失败分析却当成全局键，导致 30 段会话被压缩成 9 个事实、留存率全是 100%。已加回归测试锁定。

## 诚实边界

- 合成数据，控制力换真实度；它隔离了要测的变量，但不含真实对话的混乱。
- LLM 判定的边际有噪声；原始判定输出全部保留，可复查，且已对人工标签校准。
- 两个臂不等于完整设计空间；LLMLingua-2 留在开关后，非默认（本环境不便下载模型）。
- `cl100k_base` 是中立代理分词器，不是各模型原生分词器。
